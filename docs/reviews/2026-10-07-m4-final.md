## What held up

- **The real boots of S2 and S3.**
  - The units, drop-ins and `42_smartconfig` on this VM are byte for
    byte the repo's.
  - No two grubenv writers ran at once.
  - In the failed boot `f11e5522`, grub-common cleared recordfail at
    94.7 s: sc's flag alone brought the menu back, the case the plan was
    written for.
  - The rescue boot wrote nothing.
  - The boot after the restore cleared the flag at 9.9 s.
  - No ordering cycle in six boots.
- **The flag, path by path.**
  - A traced every kind of boot: normal, the fstab wait, stuck in
    emergency, a reset at each point, Ubuntu's recovery entry,
    hibernate, isolate, soft-reboot.
  - Only the paths found below went wrong.
- **`42_smartconfig`.**
  - 17 fabricated configurations: kernel order, an `rw` overruled,
    quotes and `$` as in `10_linux`, a separate `/boot`.
  - `grub-script-check` passes wherever `grub-mkconfig` would.
- **The GRUB password recipe**, run through the real `grub-mkconfig` on
  copies: exactly one unrestricted entry, stock output byte for byte this
  VM's `grub.cfg`.
- **sulogin, probed.**
  - With a locked root, `--force` or not, it gives a root shell.
  - With a root password, it asks for it, and three wrong ones give no
    shell.
- **The read-only store.** A hot journal, a WAL with no `-shm`, a zero
  journal, a journal that is a directory and a torn database each give
  one line; the store and the target are never changed.
- **The boots file and `sc status`.**
  - The boundary is a row id, so a clock that lags (the rescue boot's,
    minutes behind) cannot move it.
  - S3's double `seen` lines count once.
  - 50 concurrent writers over a rotation lost no line.
  - No control byte reaches the console; 4000 changed paths take 0.6 s.
- **Removal.** The README's removal leaves a `grub.cfg` that never reads
  the flag, so a flag left set is inert.
- **Nothing is built ahead of the milestone.**
